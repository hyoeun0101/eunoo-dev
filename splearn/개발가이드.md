# Splearn 개발 가이드

## 아키텍처
- 헥사고날 아키텍처
- 도메인 모델 패턴

### 계층
- Domain Layer: 핵심 비즈니스 로직을 담당
- Application Layer: 비즈니스 흐름을 조율하는 역할
- Adapter Layer : 외부(Actor)와 애플리케이션을 연결하는 통로 역할

> 의존성 방향: 외부(Actor) -> 어댑터 -> 애플리케이션 -> 도메인

## 패키지 구조
- domain
- application
  - provided : 기능 제공 애플리케이션
  - required : 기능 요구 애플리케이션
- adapter
  - webapi
  - persistence
  - integration : 이메일 발송, 외부 서비스 연동 등
  - security



## 개발 과정 정리
1. Member 도메인 개발
2. Member 도메인 순수 단위 테스트 작성
3. 리팩토링
4. 애플리케이션 계층 개발
5. 애플리케이션 계층 테스트
6. 애플리케이션 계층 구현 개발
7. 어댑터 개발: api 개발
8. 어댑터 테스트: WebMvc 테스트 작성
9. ArchUnit 이용한 아키텍처 테스트 작성



## 각 계층의 테스트 코드
- 각 계층에선 어떤 것을 중심으로 검증해야 할까?

- 도메인 계층
  - 비즈니스 로직을 검증해야 함.
  - ex) 회원을 등록하면 회원 상태가 PENDING이 맞는지 확인
  - ex) PENDING이 아닌 회원을 activate 하면 예외가 나는지 확인
  - 순수 단위 테스트로 작성. 스프링도 DB도 목도 없이 `new`로 만들어서 검증.
  - `MemberTest`, `EmailTest`

- 애플리케이션 계층
  - 포트 간의 상호작용이 올바르게 동작하는지 검증해야 함. 유스케이스가 규칙대로 동작했나 검증해야 함.
  - ex) 회원을 등록하면 id가 생기는지, 메일을 전송하는지 확인
  - ex) 중복 이메일이면 예외가 나는지, 잘못된 요청이 서비스 진입 전에 걸러지는지 확인
  - Mockito를 이용한 단위 테스트로 작성할 수 있음. 그러나 Mock은 포트 간의 관계를 검증하진 못함.
  - 의존성 검증도 할 수 있는 @TestConfiguration + @SpringBootTest를 사용한 통합 테스트로 작성.
    - `@Transactional`로 롤백. `em.flush()`로 실제 SQL을 실행시킴.
  - `MemberRegisterTest`, `MemberFinderTest`

- 어댑터 계층
  - 포트 호출이 제대로 이뤄지는지 검증한다. 비즈니스 규칙은 검증 대상이 아니다.
  - 방향에 따라 둘로 나뉜다.
    - 인바운드: 외부에서 포트를 호출함. (HTTP 요청 -> 포트)
    - 아웃바운드: 포트에서 외부를 사용. (포트 -> DB, 메일)

  - 인바운드 어댑터 (웹) : `MemberApiWebMvcTest`
    - 하는 일: HTTP 요청을 받아 포트를 호출하고, 결과를 JSON과 상태 코드로 응답한다.
    - 검증할 것: URL 매핑, JSON 직렬화/역직렬화, 상태 코드, 요청 검증 실패 처리
    - ex) 잘못된 이메일로 요청하면 포트를 호출하지 않고 400으로 막히는지 확인
    - `@WebMvcTest(MemberApi.class)` 슬라이스 + 포트는 `@MockitoBean`으로 대체.
      - 여기서는 목이 정답이다. 확인할 것이 "포트를 올바르게 호출했는가"라서,
        포트 뒤에 진짜 서비스가 있든 목이 있든 결과가 같아야 정상이다.
      - 컨트롤러 관련 빈만 올라오므로 DB도 서비스도 필요 없고, 그만큼 빠르다.

  - 아웃바운드 어댑터 (영속성) : `MemberRepositoryTest`
    - 하는 일: 포트 구현체로서 실제 DB에 저장하고 조회한다.
    - 검증할 것: 엔티티 매핑, 제약조건, 직접 선언한 쿼리 메서드
    - DB에 데이터가 들어갔는지 직접 확인한다.
    - ex) 저장 -> `flush` -> `clear` -> 다시 조회해서 값이 살아 돌아오는지 확인
      - `clear`가 없으면 1차 캐시에 있던 객체가 그대로 나온다. 매핑이 틀려도 테스트가 통과해버린다.
    - ex) 유니크 제약이 DB에 실제로 걸려 있어서 중복 저장이 실패하는지 확인
    - `@DataJpaTest` 슬라이스. JPA 관련 빈만 올라온다.

  - 아웃바운드 어댑터 (그 외 구현체) : `SecurePasswordEncoderTest`
    - 하는 일: 비밀번호 암호화, 메일 발송처럼 DB가 아닌 바깥 일을 처리한다.
    - 검증할 것: 그 구현체 하나의 동작. 누가 호출하는지는 관심 없다.
    - ex) 인코딩한 비밀번호가 `matches`로 다시 검증되는지 확인
    - 스프링 없이 `new`로 만들어서 검증. 도메인 테스트와 방식이 같다.

- 전 계층 통합 (E2E)
  - 각 계층이 실제로 맞물려 돌아가는지 검증. 빈 설정, 트랜잭션, 예외 -> 상태 코드 매핑처럼 슬라이스에서는 볼 수 없는 것을 확인.
  - ex) 중복 이메일로 POST 하면 409가 내려오는지 확인
  - `@SpringBootTest` + `@AutoConfigureMockMvc` + `@Transactional`.
  - 느리므로 핵심 시나리오만 얇게 유지.
  - `MemberApiTest`
